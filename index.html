Compiler status

    Compiler Optimization Research

    This website documents the development of a custom compiler and the research conducted for my thesis: the design and implementation of a didactic compiler for x86-64 and the evaluation of the impact of classic optimizations, compared with the performance of GCC and LLVM.

    The main focus of the project is studying the impact of compiler optimizations and comparing their results with established compilers.

    Introduction

    Compiler optimization is the process of transforming a program in order to improve characteristics such as execution time, memory usage or generated code size, while preserving the program's behavior.

    Production compilers such as GCC and LLVM group their optimizations into levels (-O1, -O2, -O3). Because the optimizations are bundled, it is hard to know how much each one contributes individually, which limits their value for learning how a compiler works internally. This is especially true for students and developers who want to understand compilers empirically and quantitatively.

    This project aims to implement several optimization techniques in a custom compiler, make each one individually switchable, and measure their effects through controlled experiments.

    Objective and Scope

    The objective of this research is to investigate how different compiler optimizations affect the performance of generated programs: to design and implement a didactic compiler for x86-64 that allows evaluating the individual and combined impact of seven classic optimizations on code quality and execution time.

    The results will be compared with optimization levels provided by established compilers such as GCC and LLVM (-O2 and -O3).

    Specific objectives

    • Build a compiler for x86-64 with lexical analysis, parsing, intermediate code generation, optimization and object code generation.
    • Implement each of the seven optimizations independently so they can be enabled or disabled one by one.
    • Create a set of test programs (benchmarks) and a measurement protocol that makes the results reproducible.
    • Measure the individual and combined effect of each optimization on execution time and on code quality metrics (instruction count, binary size).
    • Compare the didactic compiler against GCC and LLVM at -O2/-O3 as a reference for achievable performance.
    • Analyze which optimizations bring the largest benefits and when their effect is limited or depends on other transformations.

    Scope

    The contribution is didactic and methodological. GCC and LLVM are used only as a reference for the maximum achievable performance; the project does not intend to compete with them or match the breadth of their optimizations. The proposed framework is reproducible and could be reused to evaluate other techniques or extended to other architectures. It can also serve as an educational resource for teaching compilers at the Instituto Tecnológico de Morelia and other TecNM institutions.

    Background

    Structure of a compiler

    A compiler is traditionally divided into an analysis phase (front-end) and a synthesis phase (back-end) (Aho et al., 2006). Lexical analysis converts the input characters into tokens; the parser checks the tokens against the language grammar and builds the Abstract Syntax Tree (AST). The compiler then generates an Intermediate Representation (IR), where architecture-independent optimizations are applied, and finally code generation emits x86-64 instructions (Cooper & Torczon, 2012).

    Intermediate representation and data-flow analysis

    Optimizations are applied on an IR commonly organized into basic blocks and a control-flow graph (Allen, 1970). Compilers rely on data-flow analysis to decide which transformations are safe, a framework formalized by Kildall (1973). Static single assignment (SSA) form makes many of these analyses simpler and more efficient (Cytron et al., 1991).

    The x86-64 architecture

    x86-64 is the 64-bit extension of x86. It has 16 general-purpose registers, variable-length instructions and SIMD extensions (SSE, AVX) (Hennessy & Patterson, 2017). The performance of generated code depends on register allocation, use of the memory hierarchy and pipelining, so the same optimization can have different effects depending on the access pattern and type of computation.

    Related Work

    Previous work falls into four lines: didactic compilers, reference compiler infrastructures, empirical evaluation of optimizations, and rigor in performance measurement.

    • Didactic compilers. Ghuloum (2006) proposed building a compiler incrementally, so each stage yields a complete working compiler. Appel (2002) and Wirth (1996) also present full compiler construction as a teaching tool, but emphasize front-end design and code generation rather than measuring the quantitative effect of each optimization.
    • Reference infrastructures. Lattner and Adve (2004) introduced LLVM, based on a typed SSA intermediate representation, where each transformation is an independent pass. This is the closest precedent to the per-optimization switching used here. GCC exposes many individual optimization flags, but their behavior depends on complex interactions between them, which makes isolated analysis difficult.
    • Empirical evaluation of optimizations. Hoste and Eeckhout (2008) explored GCC optimization levels to find flag combinations that beat the standard levels. Maleki et al. (2011) evaluated how well production compilers vectorize different code patterns and found that it varies between compilers. Ashouri et al. (2018) surveyed compiler autotuning with machine learning, showing the importance of choosing which optimizations to apply. These studies analyze production compilers or existing flag sets, not a didactic compiler with optimizations decoupled by design.
    • Measurement rigor. Mytkowicz et al. (2009) showed that seemingly irrelevant factors, such as environment size or link order, can significantly change performance results and lead to wrong conclusions. Georges et al. (2007) argued for statistically rigorous evaluation using repetitions and confidence intervals.

    Identified gap

    The reviewed works address didactic compiler construction, evaluation of production compilers, or measurement methodology, but do not integrate the three in a reproducible framework that measures the individual and combined effect of classic optimizations in a didactic compiler contrasted with GCC and LLVM. This research aims to fill that gap.

    Experiments

    Experiments will be used to measure the effect of individual optimization techniques.

    Experiment 001 — Constant Folding

    Evaluates expressions whose operands are known constants at compile time (for example, replacing x = 3 + 5 with x = 8), avoiding calculating the sum during every execution (Aho et al., 2006; Muchnick, 1997).

    Status: Planned

    Experiment 002 — Constant Propagation

    Replaces subsequent uses of a variable with its known constant value at a given point in the program. For example, if a = 10 and later b = a + 2 is used, it can be rewritten directly as b = 12 when combined with constant folding. See also Wegman and Zadeck (1991) for propagation with conditional branches.

    Status: Planned

    Experiment 003 — Dead Code Elimination (DCE)

    Removes instructions whose results are never used or that are unreachable (such as code following a return statement or variables assigned but never read), reducing code size without changing observable behavior. It often takes advantage of opportunities left by the previous optimizations (Muchnick, 1997).

    Status: Planned

    Experiment 004 — Common Subexpression Elimination (CSE)

    Detects when the exact same expression is calculated multiple times with identical, unchanged operands, reusing the previously calculated result instead of recomputing it (Cocke, 1970).

    Status: Planned

    Experiment 005 — Loop-Invariant Code Motion (LICM)

    Identifies computations inside a loop whose results do not change across iterations and moves them outside the loop so they execute only once instead of every iteration. It requires identifying the loops and verifying that the motion preserves semantics (Aho et al., 2006; Cooper & Torczon, 2012).

    Status: Planned

    Experiment 006 — Loop Unrolling

    Reduces the number of iterations in a loop by replicating its body multiple times within a single iteration, decreasing loop control overhead (comparisons, jumps, counter increments) at the cost of larger code size, which can affect the instruction cache (Dongarra & Hinds, 1979; Davidson & Jinturkar, 1995).

    Status: Planned

    Experiment 007 — Auto-vectorization

    Transforms repetitive scalar operations (such as element-by-element array addition) into SIMD instructions that process multiple data points in parallel using processor vector registers (such as SSE/AVX on x86-64). Superword-level parallelism (SLP) is a key method for finding these opportunities (Larsen & Amarasinghe, 2000). Success depends on the operations being independent and the data being well aligned in memory (Allen & Kennedy, 2002; Maleki et al., 2011).

    Status: Planned

    Interaction between optimizations

    Optimizations are not independent. Constant folding and propagation generate dead code that DCE removes, and unrolling can expose common or invariant subexpressions that other transformations exploit (Muchnick, 1997). For this reason, besides the individual effect, the research measures the combined effect and analyzes the interactions between techniques.

    Methodology

    The method consists of building a complete compilation pipeline (lexical phase, parsing, IR generation, optimization passes and x86-64 machine code emission) and running comparative tests with different optimization configurations, using GCC and LLVM at -O2/-O3 as the performance reference.

    Measurement protocol

    • Metrics: execution time, number of instructions and binary size.
    • Configurations: each optimization enabled alone, and in combinations, compared with a baseline without optimizations.
    • Rigor: repeated runs, a controlled environment, and reporting of variability (mean and standard deviation), since measurement bias can produce wrong results (Mytkowicz et al., 2009; Georges et al., 2007).
    • Reference: the -O2 and -O3 levels of GCC and LLVM serve as achievable performance, not as direct competitors.

    The expected outcome is quantitative evidence of how much each optimization contributes to execution time, and a comparison between a didactic environment and industrial compilers.

    Research

    Research question

    What is the impact of selected compiler optimizations on the performance of programs generated by a custom compiler compared with established compiler optimization levels? More precisely: how do classic optimizations in a didactic x86-64 compiler affect the quality of the generated code and its execution time, and how close are these results to those of production compilers such as GCC and LLVM?

    Relevance

    • Practical: being able to enable and disable optimizations independently shows how each transformation changes the generated code and its performance, helping build technical judgment for optimization decisions.
    • Methodological: a reproducible framework that combines compiler construction, benchmark selection and a measurement protocol.
    • Institutional: an educational resource for teaching compilers.
